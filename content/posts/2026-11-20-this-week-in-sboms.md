This is the fifth **This Week in SBOMs**, covering **Saturday 14 to Friday 20 November 2026**. [Last week](/2026/11/13/this-week-in-sboms-2026-11-13/) the build system was the target. This week it was the runtime: three language runtimes and the web server that sits in front of half of everything all shipped critical fixes within roughly three days. All of them tend to be bundled inside someone else's product.

On the regulatory side, the CRA finally has published standards, and two national parliaments moved.

## The big one: Java4Shell, and the runtimes nobody lists

On **17 November** OpenJDK published its [quarterly advisory](https://openjdk.org/groups/vulnerability/advisories/2026-11-17). The headline is [CVE-2026-114938](https://insights.sbomify.com/CVE-2026-114938/) in `hotspot/compiler`, CVSS 8.1, which [Calif](https://calif.io/java4shell/) named **Java4Shell**. The bug is in the hand-written AVX-512 VBMI assembly that HotSpot uses to speed up Base64 decoding on x86-64. A crafted input makes the routine compute a negative output length and write past the end of the array. Calif says it "affects OpenJDK from version 17.0.6 or newer" on CPUs with AVX-512 VBMI, and "ARM64 CPUs are not affected". The advisory lists the affected versions as "27.0.1.0.3, 25.0.5.0.3, 21.0.13.0.3, 17.0.21.0.3, 11.0.33, 8u512, and earlier". Mitigations until you can patch are `-XX:-UseBASE64Intrinsics` or `-XX:UseAVX=2`, on x86-64 only.

CISA issued an [alert](https://www.cisa.gov/news-events/alerts/2026/11/17/critical-java-vulnerability-requires-immediate-patching) the same day, and it reads like an SBOM brief: "Review your software inventory for JDKs and Java runtimes, including those bundled with third-party applications or included in container images and appliances." It adds: "Note: JDKs and Java runtimes may not appear as separate entries in software inventories." Germany's BSI [warned](https://www.bsi.bund.de/SharedDocs/Cybersicherheitswarnungen/DE/2026/2026-306673-1032_bits.html) on 18 November that GreyNoise was already seeing first exploitation attempts. CERT-In [followed](https://www.cert-in.org.in/s2cMainServlet?pageid=PUBVLNOTES02&VLCODE=CIAD-2026-0061) the same day. Java4Shell is not in KEV. On oss-security, Solar Designer [noted](https://www.openwall.com/lists/oss-security/2026/11/19/5) that a fix for the same code had been proposed and closed without merging three months earlier. ([THN](https://thehackernews.com/2026/11/java4shell-cve-2026-114938-enables-pre.html), [HN](https://news.ycombinator.com/item?id=50538240))

**Why this matters for SBOM/VEX practitioners:** this is Log4Shell's lesson again, one layer down. Calif lists Keycloak, Jira, Confluence, Artifactory, Jenkins and PingFederate as reachable in default configurations. Several ship their own runtime: [Keycloak says](https://www.keycloak.org/2026/11/java4shell-vulnerability-cve-2026-114938) its "x86-64 Keycloak container images tagged 26.8.2-1 and 26.8.2-2 bundle an affected OpenJDK 21.0.13 build". If your SBOMs record the JDK as a component with its exact build version, this is a query. If they stop at the application, it is a week of tickets to vendors. Exploitability also depends on the CPU, which is a rare case where a hardware fact belongs in a VEX justification. "Not affected: ARM64 deployment" is legitimate, but only if you can prove where the workload runs.

## Security news that mattered

**NGINX2Root: two HTTP/2 RCEs in nginx (18 November).** nginx 1.30.7 and 1.31.9 fix [ten issues](https://nginx.org/en/security_advisories.html). Two are memory-safety bugs in HTTP/2: [CVE-2026-123007](https://insights.sbomify.com/CVE-2026-123007/), "Memory corruption in HTTP/2 flow control" (nginx severity: major, vulnerable 1.9.5 to 1.31.8), and [CVE-2026-123633](https://insights.sbomify.com/CVE-2026-123633/), a use-after-free (nginx severity: medium, vulnerable 1.19.7 to 1.31.8). [Wiz](https://www.wiz.io/blog/nginx-http2-rce-vulnerabilities) is one of five teams credited with finding them independently. The "root" half depends on a separate, undisclosed Linux SCTP privilege escalation; its finders say that fix "will be released in the coming weeks" ([oss-security](https://www.openwall.com/lists/oss-security/2026/11/18/16)). The interim mitigation is `http2 off`. ([THN](https://thehackernews.com/2026/11/10-year-old-nginx-http2-flaw-lets.html), [HN](https://news.ycombinator.com/item?id=50547374)) _Why it matters:_ nginx is embedded in appliances, ingress controllers and products like GitLab. An HN thread already asks why [GitLab 19.6.0](https://news.ycombinator.com/item?id=50561571) still ships vulnerable versions. Your vendors' SBOMs should name the nginx version; ask for them.

**Ruby2Shell and six more Ruby bugs (18 November).** Ruby [released](https://www.ruby-lang.org/en/news/2026/11/18/multiple-vulnerabilities-in-regexp-and-string/) 4.0.10, 3.4.13 and 3.3.14 for seven flaws in the regex engine and string case conversion, saying "We are aware of PoCs that prove some of them can be used to trigger remote code execution." The one [Veria Labs](https://verialabs.com/ruby2shell/) named Ruby2Shell, [CVE-2026-132825](https://insights.sbomify.com/CVE-2026-132825/), is a one-byte heap overflow that it says is reachable pre-auth on default Rails and Sinatra apps. Ruby 3.2 and earlier are end-of-life and get no fix. Veria's line is the SBOM point in one sentence: "These products bundle their own Ruby, so the fix has to come from the vendor." Its table lists GitHub Enterprise Server 3.22.5 and earlier with no fixed release yet. ([THN](https://thehackernews.com/2026/11/ruby-releases-fixes-for-7-regex-and.html), [HN](https://news.ycombinator.com/item?id=50556287))

**PHP fixes seven Critical issues (19 November).** PHP 8.6.0, 8.5.13, 8.4.28, 8.3.37 and 8.2.36 fix 17 advisories ([php.net](https://www.php.net/archive/2026.php), [GHSAs](https://github.com/php/php-src/security/advisories)) and bundle uriparser 1.0.3. The pre-announcement said the Critical ones "require either non-default configuration or uncommon setups". One is supply-chain shaped: [CVE-2026-128090](https://insights.sbomify.com/CVE-2026-128090/), a Phar OpenSSL signature bypass through algorithm downgrade. ([THN](https://thehackernews.com/2026/11/php-fixes-7-critical-flaws-including.html)) _Why it matters:_ after PHP2Shell, [we noted](/2026/11/13/this-week-in-sboms-2026-11-13/) that PHP compiled into official Docker images is owned by no package manager. The same applies to these fixes.

**Microsoft's agent-framework compromised on PyPI (17 November).** [Socket](https://socket.dev/blog/agent-framework-pypi-package-compromised-with-credential-stealer) reports that `agent-framework` 1.26.1 and 1.26.2 were published on 17 November with `.pth` startup hooks. These run on every Python start, including `pip` itself. The hooks collected environment secrets and Azure CLI, npm, Git and Docker credential files, and requested fresh Azure managed-identity and DevOps OIDC tokens. Both versions are gone; PyPI now shows 1.26.0 as the latest. According to THN, Microsoft said it had made "some repositories private while we investigate", and `microsoft/onnxruntime` returned 404 when we checked. How the attacker obtained publish access has not been disclosed. ([THN](https://thehackernews.com/2026/11/attackers-compromise-microsofts-agent.html), [HN](https://news.ycombinator.com/item?id=50539610)) _Why it matters:_ search your SBOMs and lockfiles for exactly these two versions. A `.pth` hook runs during the build, so check build hosts and CI runners as well as deployed environments.

**Optimizely snippets served injected JavaScript (16 to 18 November).** Optimizely [says](https://status.optimizely.com/incidents/ftw0fh9wx43z) an attacker "exploited a flaw in the Optimizely Web Experimentation account signup flow" to inject code into customer projects, affecting "Less than 5% of our customers". [Report URI](https://blog.report-uri.com/worlds-largest-brands-infected-with-malware-via-optimizely/) found the code in 188 of 1,611 snippets it checked, including a card skimmer. ([Krebs](https://krebsonsecurity.com/2026/11/attackers-used-optimizely-to-a-b-test-malware-on-top-websites/), [THN](https://thehackernews.com/2026/11/hijacked-optimizely-scripts-served-card.html), [HN](https://news.ycombinator.com/item?id=50524767)) _Why it matters:_ third-party scripts loaded at runtime never appear in a build-time SBOM. If you inventory web front ends, list external script origins as services.

**Also worth your time:**

- **OpenSSL** [pre-announced](https://www.openwall.com/lists/oss-security/2026/11/17/6) three Low fixes for 4.1.1, 4.0.4 and 3.5.10 on 1 December. Separately, [CVE-2026-121481](https://insights.sbomify.com/CVE-2026-121481/) in `EVP_EncodeBlock()` is rated Low by OpenSSL ("No path by which an attacker can trigger this has been identified"). CISA-ADP nonetheless added a CVSS 9.8 to the record, and an [HN thread](https://news.ycombinator.com/item?id=50569226) carried the 9.8 in its title. This is a good case for a VEX statement rather than a fire drill.
- **Apache Roller** [CVE-2026-129448](https://insights.sbomify.com/CVE-2026-129448/), an unauthenticated deserialisation bug fixed in 6.1.6, "is being actively exploited" according to the [ASF](https://www.openwall.com/lists/oss-security/2026/11/17/5). It was not in KEV as of the 18 November catalogue.
- **SSHole follow-up:** Solar Designer [reports](https://www.openwall.com/lists/oss-security/2026/11/16/1) that musl will likely move to the same `*0`/`*1` failure tokens as libxcrypt before eventually returning NULL. We found nothing new from Buildroot.

**KEV.** Five additions in the window, catalogue version 2026.11.18. Two are open-source components. BerriAI LiteLLM [CVE-2026-40217](https://insights.sbomify.com/CVE-2026-40217/) is due 2 December; this is an AI gateway that many teams pull in as a Python dependency. Apache Axis [CVE-2026-90436](https://insights.sbomify.com/CVE-2026-90436/) is due 21 November; it is an old transitive Java library that Rapid7 reports was exploited through Confluence Data Center, which embeds it. The others are Puppet Enterprise [CVE-2026-115731](https://insights.sbomify.com/CVE-2026-115731/), Synology DSM [CVE-2024-10441](https://insights.sbomify.com/CVE-2024-10441/) and REDCap [CVE-2026-90817](https://insights.sbomify.com/CVE-2026-90817/). See our [KEV explainer](/2025/12/30/what-is-kev-cisa-known-exploited-vulnerabilities/).

## CRA

**The first CRA standards are published (18 to 19 November).** CEN-CENELEC [announced](https://www.cencenelec.eu/news-events/news/2026/en-in-the-spotlight/2026-11-19-cra-standards-en-40000-1-1-and-en-40000-1-2/) "the publication of two new European Standards: EN 40000-1-1 on cybersecurity terminology and EN 40000-1-2 on cybersecurity principles, product risk management and lifecycle activities". FprEN 40000-1-3 and the first vertical standards are to follow; the Commission [counts](https://digital-strategy.ec.europa.eu/en/news/first-european-standard-published-support-cyber-resilience-act) "over 30 standards in the making". We found no Official Journal reference, so neither standard yet carries a presumption of conformity. _Why it matters:_ 1-2 is the risk-management and lifecycle backbone that the SBOM and vulnerability-handling parts will hang off. Vulnerability handling is in 1-3, which is not out yet. Background is on our [CRA page](/compliance/eu-cra/).

**Germany: the Bundesrat clears the CRA act (20 November).** In session 1070 the Bundesrat [decided](https://www.bundesrat.de/drs.html?id=621-26%28B%29) not to call the mediation committee on the implementation act the Bundestag passed on 15 October (Drucksache 621/26). The law can now go for signature and promulgation. According to the Bundesrat's [explanatory note](https://www.bundesrat.de/SharedDocs/TO/1070/erl/7.pdf?__blob=publicationFile&v=1), the BSI becomes the market surveillance and notifying authority and will support SMEs and open-source software stewards. _Why it matters:_ the authority that will read German manufacturers' SBOMs is also the one that wrote [TR-03183](/compliance/bsi-tr-03183/).

**ENISA: SRP 1.4 and a notified-body gap analysis.** The [SRP page](https://www.enisa.europa.eu/topics/product-security/vulnerability-services/eu-incident-response-and-cyber-crisis-management/single-reporting-platform-srp) says that on 17 November the platform "was upgraded to version 1.4". The documentation "is currently being updated", and ENISA has published no changelog. On 16 November ENISA published a [gap analysis](https://www.enisa.europa.eu/publications/cra-module-b-and-h-cabs-accreditation-for-notification) of notified-body accreditation for CRA Modules B and H. It says assessors need the competence "to assess machine-readable SBOMs and verify their completeness and consistency against the TOE", with familiarity with "CycloneDX 1.4 or higher or SPDX 2.3 or higher". The document is non-binding, but it is the clearest statement yet of the SBOM floor a third-party assessor will expect.

**Eclipse ORC.** The due-diligence task force [merged](https://github.com/orcwg/cra-due-diligence) a proposal on what open-source projects provide, which says "Licensing metadata should be captured directly within standardized Software Bills of Materials". The CRA FAQ did not grow this week.

## NIS2

**France: the Assemblée nationale adopts the resilience bill (17 November).** The bill transposing NIS2 and CER [passed](https://www.assemblee-nationale.fr/dyn/actualites-accueil-hub/adoption-du-projet-de-loi-relatif-a-la-resilience-des-infrastructures-critiques-et-au-renforcement-de-la-cybersecurite) at first reading, 464 to 64 ([scrutin 9916](https://www.assemblee-nationale.fr/dyn/17/scrutins/9916)). The Senate adopted its own version in March 2025, so the texts still need reconciling. It is not law yet.

The 19 November infringement package had no NIS2 actions. See our [NIS2 page](/compliance/eu-nis2/).

## CISA and US regulators

Beyond the Java4Shell alert and KEV, it was quiet. The Federal Register had no hits in the window for "software bill of materials", SBOM, "cryptographic inventory", "secure software development" or FASCSA. CISA published no SBOM, VEX or Secure by Design material, and the [2026 Minimum Elements](/compliance/cisa-minimum-elements/) are unchanged. NIST [announced](https://csrc.nist.gov/News/2026/nist-will-revise-tls-guidelines) on 19 November that it will revise SP 800-52 Rev. 2 to "Add support for post-quantum algorithms" and deprecate weaker TLS 1.2 suites. Another nudge towards a [CBOM](/faq/what-is-a-cbom/).

## Other regulators

**UK financial regulators name SBOMs and cryptographic inventories (19 November).** The Bank of England, PRA and FCA opened consultation [GC26/9](https://www.fca.org.uk/publications/guidance-consultations/gc26-9-cyber-risk-resilience-management) on cyber resilience guidance, closing 26 February 2027. It expects firms to "keep an up-to-date inventory of their key assets, third-party dependencies and cyber risks". The accompanying [AI effective practices](https://www.bankofengland.co.uk/prudential-regulation/publication/2026/november/effective-practices-cyber-risk-and-resilience-management-relating-to-artificial-intelligence) list "software bills of materials" among the sources for identifying exposures. The [quantum effective practices](https://www.bankofengland.co.uk/prudential-regulation/publication/2026/november/effective-practices-cyber-risk-and-resilience-management-relating-to-quantum-computing) describe "a 'cryptographic inventory'" for planning PQC migration. The FCA [says](https://www.fca.org.uk/news/press-releases/uk-financial-watchdogs-clarify-cyber-expectations-attacks-rise) October incident reports were "52% above the previous high recorded in May 2025". _Why it matters:_ this is guidance, not a mandate. Still, UK-regulated firms and their suppliers now have supervisors pointing at SBOMs and CBOMs by name.

**Germany.** The BSI's [annual report](https://www.bsi.bund.de/DE/Service-Navi/Presse/Pressemitteilungen/Presse2026/261119_Lagebericht.html) (19 November) counts 160 new vulnerabilities a day and says time-to-exploit fell to eight days in Q2 2026. TR-03183 is unchanged.

**UK Bill.** Commons consideration of Lords amendments to the Cyber Security and Resilience Bill is still set for 24 November. The amendment papers did not load for us, so we cannot say whether any touch the software supply chain.

Nothing new from METI, CSA Singapore or CERT-In on SBOMs; Australia and Canada did not load.

## Standards

**VERS 1st edition is ready for the Ecma GA (17 November).** Ecma TC54 [tagged](https://github.com/Ecma-TC54/ECMA-xxx-VERS/releases/tag/edition-1.0.0) `edition-1.0.0`, which "matches the content submitted to the Ecma GA for review and approval at the December GA meeting". [vers-spec v1.2.2](https://github.com/package-url/vers-spec/releases/tag/v1.2.2) brings the community spec in line. _Why it matters:_ VERS is the version-range syntax that VEX and advisory tooling will cite. This is the text it will be cited as.

**A PURL registry for software outside public registries.** A proposed [design document](https://github.com/package-url/purl-spec/tree/main/docs/design) landed in purl-spec on 17 November. It tackles what it calls "One of the biggest challenges for universal PURL adoption": identifying "Commercial or proprietary software including internal use only software". It builds on the `software-id` type, where the namespace starts with an internet domain, and has publishers serve a `/.well-known/purl.json`. It is only a proposal, but it targets the C/C++ and proprietary-component gap that hurts SBOM matching most.

**CycloneDX.** Still 1.7.2, so the November target for 2.0 has not been met so far. A new umbrella issue, [#1221](https://github.com/CycloneDX/specification/issues/1221), aims to "create one source of truth" for how 2.0 references ISO and RFC formats, which suggests the schema is not frozen. On 1.x, [#1219](https://github.com/CycloneDX/specification/pull/1219) adds Composite ML-DSA to the cryptography registry for CBOM generators. We found no minutes for TC54's 12 November discussion of normative references to SPDX.

**SPDX.** Still 3.1 RC1. [#1474](https://github.com/spdx/spdx-3-model/pull/1474) recommends SHA-256 or stronger, says MD5 and SHA-1 are not collision resistant, and deprecates the Dilithium, Kyber and FALCON entries "because they are not hash algorithms". New issue [#1495](https://github.com/spdx/spdx-3-model/issues/1495) notes that after 2.3 to 3.0 conversion "a converted SBOM can no longer say whether a patch has been" applied. That matters if you track distro backports.

## The wider landscape

- **OpenSSF:** the TAC vote ratifying the Supply Chain Integrity working group charter [passed](https://github.com/ossf/tac/issues/682) 8 to 0 on 19 November. A [17 November post](https://openssf.org/blog/2026/11/17/clearer-security-signals-making-attestations-comprehensible-for-pypi-users/) says PyPI now has redesigned project pages with "a dedicated security tab" for attestations.
- **Dependency-Track 5.2.2 and 4.14.7 (18 November):** [5.2.2](https://github.com/DependencyTrack/dependency-track/releases) updates the default ENISA EU KEV catalogue source and fixes CEL policies "not taking analysis overrides into account". If you record VEX-style analyses in Dependency-Track, that second fix matters.
- **CycloneDX tooling:** [cdxgen 13.8.0](https://github.com/cdxgen/cdxgen/releases) (14 November) "closes twenty-six advisories". 12.9.3 backports a fix where "scanned content could make cdxgen run project tooling": your SBOM generator runs on untrusted input. [cyclonedx-python 9.0.0](https://github.com/CycloneDX/cyclonedx-python/releases) adds an opt-in `--add-python-runtime`, which adds the interpreter itself as a component.

## House news: sbomify v26.11.1 lets releases retire

This column leaves vendor announcements out, so this one is flagged as ours. On 17 November we shipped [sbomify v26.11.1](/2026/11/17/announcing-sbomify-v26-11-1-the-one-that-lets-releases-retire/) ([release notes](https://github.com/sbomify/sbomify/releases/tag/v26.11.1)). It gives every release a lifecycle. A release can declare what it replaces, either on the **same line** (1.2.4 retires 1.2.3) or as a **new line** (2.0 follows 1.2, and both stay supported), and it can carry end-of-support and end-of-life dates. From CI, `POST /api/v1/releases` takes a `supersedes` list that names the predecessor by its version.

sbomify then monitors only what is live. Scheduled scans, the VEX re-apply and Dependency-Track all cover live releases and each component's newest build, and nothing older. Releases past their support date retire on their own. A retired release shows when it was last scanned and why scanning stopped, instead of presenting old counts as current. Dependency-Track is now laid out by release series, so a replacement takes over its predecessor's projects and your audit decisions with them. The model follows the [Common Lifecycle Enumeration](/compliance/cle/) (ECMA-428).

_Why it matters:_ a week like this one, with Java, Ruby, PHP and nginx all fixing critical bugs, is when you need to know which releases you still owe customers a fix for. The CRA asks the same question through support periods. Self-hosters should read the upgrade notes first: there is a one-off Dependency-Track backfill, and Redis is replaced by Valkey.
